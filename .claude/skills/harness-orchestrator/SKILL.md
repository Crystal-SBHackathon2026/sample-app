# 하네스 오케스트레이터 (도메인-무관)

전문 에이전트들을 파이프라인 + 3중 생성-검증 루프(계획·개발·PR)로 조율해, 사용자의 개발 요청을 계획부터 PR·설명·완료감사까지 완결한다. 도메인 지식은 이 스킬에 없다 — 전부 `.claude/harness/project-profile.md`(프로필)에서 온다.

**실행 모드: 에이전트 팀.** 개발↔검수, PR작성↔PR점검 사이의 피드백 루프가 있어 팀 통신이 유리하다. 모든 Agent 호출에 `model: "opus"`를 명시한다.

**스킬 통제권:** 전역 using-superpowers의 "응답 전 스킬 먼저" 선점은 이 하네스에서 비활성(CLAUDE.md 지시). 어떤 superpowers 스킬을 언제 쓰는지는 각 에이전트 정의와 이 오케스트레이터가 결정한다.

## Phase 0: 컨텍스트 확인 + 도메인 로드

1. **실행 모드 판별 + RAM 재개:**
   - `_workspace/progress.md`가 있으면 **가장 먼저 읽는다** — 진행 중 작업의 현재 상태(완료 단계·다음 단계·미해결 결정). 세션이 바뀌었어도 여기서 이어받는다. 없고 새 작업이면 생성한다.
   - `_workspace/` 존재 + 부분 수정 요청("검수만 다시", "PR만") → **부분 재실행** (해당 에이전트만 — 리뷰 게이트면 그 Phase 의 cc·cx 한 쌍, 아래 해당 Phase로 점프)
   - `_workspace/` 존재 + 새 입력 → **새 실행** (기존을 `_workspace_prev/`로 이동)
   - `_workspace/` 미존재 → **초기 실행**
2. **프로필·원칙 로드(오케스트레이터가 직접 1회 Read):** `.claude/harness/project-profile.md` + `.claude/harness/principles.md`. 이후 각 에이전트 dispatch 시 아래 주입 규칙대로 **해당 섹션 전문을 Task 프롬프트에 동봉**한다 — 에이전트가 "읽으러 갈지"를 선택에 맡기지 않는다.
3. **정본 드리프트 확인(초기 실행 시 1회):** 이 스킬·훅이 템플릿 정본(kty-claude-harness-template)과 다르면 — 특히 "듀얼 리뷰 규칙" 절이나 `guard-codex-invocation.sh`가 없으면 — 작업 전에 `sync.sh <프로젝트>`부터 실행한다. 근거: 2026-08-03 POK-30에서 sync 누락으로 구버전 스킬(Phase 3만 codex)을 따라 설계 단계 듀얼 리뷰가 생략된 실사고.
4. **과거 기억 검색(초기 실행 시 1회):** `claude-mem:mem-search` 스킬을 호출해 "전에 이 문제/유사 요청을 풀었나"를 검색(search→timeline→get_observations 3층 워크플로우). 관련 결과가 있으면 clarifier·ecc:planner 프롬프트에 요약 동봉. (claude-mem은 2세션째부터 자동 주입도 하므로, 명시 검색은 착수 시 1회면 충분.) 검색 결과에 하중지지 사실(확정 결정·규칙)이 있으면 파일 메모리로 승격을 제안한다. **폴백:** claude-mem 비활성/미설치면 `_workspace_prev/`·git 이력을 대체 소스로 쓴다 — 보고에 "claude-mem 미사용"을 명시한다.

   **지식 진입점과의 분업 (ADR-0013 ⑤):** claude-mem 은 "전에 무엇을 **했나**"(세션 히스토리 — 유사 작업·과거 시도), 프로필 9절 진입점은 "전에 무엇을 **정했나**, 왜"(결정 기록 — architect·planner 착수 전, clarifier 질문 전, ADR 작성 전). 둘이 어긋나면 **진입점 쪽을 따르고 어긋남 자체를 사용자에게 보고한다** — 사용자가 진입점을 슬롯으로 지정했다는 사실이 "이쪽을 정본으로 참조하라"는 바인딩이다(진입점 기록이 낡았을 수도 있으니 판정은 사용자 몫).

### 외부(ECC) 참조 에이전트 dispatch 계약

설계·계획·검수·보안검수 4역할은 자체 에이전트가 아니라 **ECC 전역 에이전트를 참조 호출**한다(2026-07-20 교체 — 만들기 전에 찾는다, `[tq]`와 같은 레이어 원칙. `[tq]`: 검수 지적 통합 태그 — 정의는 Phase 3). ECC 정의에는 하네스 계약이 없으므로, dispatch할 때마다 아래 계약을 **Task 프롬프트에 명시**한다. ECC 플러그인이 없는 환경이면 동명 전역 에이전트(`~/.claude/agents/`)로 대체하고, 그것도 없으면 해당 역할을 오케스트레이터가 직접 수행하되 보고에 "ECC 미설치 — 대체 수행"을 명시한다(조용한 성공 위장 금지).

**공통 계약(4종 모두 프롬프트에 포함):** ① 한국어로 출력 ② 주입된 프로필·principles.md(제0원칙 **및 '스타일 정본' 절**)를 판단 기준으로 사용 ③ 산출물은 응답 본문으로 반환 — `_workspace/` 파일 저장은 오케스트레이터가 수행 ④ 확인 못 한 항목은 지어내지 말고 "미확인"으로 표기 ⑤ **스타일 판단은 Google 스타일 가이드가 최상위 정본이다** — 코드·문서를 쓰거나 스타일을 지적하기 전에 `google-styleguide` 스킬을 호출하고, 지적에는 정본 근거(`파일 — 조항`)를 적는다.

## 듀얼 리뷰 규칙 — 모든 검증 게이트 공통 (2026-08-01 사용자 확정 — ADR-0020)

**모든 리뷰 게이트는 Claude + Codex 듀얼로 돈다** — plan-reviewer의 설계/계획 각 pass(Phase 2), ecc:code-reviewer 검수(Phase 3), pr-reviewer 점검(Phase 4) 전부. Claude 리뷰어 dispatch와 **병렬로** Codex를 호출한다:

```bash
codex exec --sandbox read-only -m gpt-6.1-sol -c model_reasoning_effort="xhigh" "<리뷰 프롬프트: 대상 파일 경로·판정 기준·출력 형식(판정 줄+심각도+시나리오)>" < /dev/null
```

### 종결 기준·라운드 규약 (2026-09-04 kty 개정 — 계획 게이트는 `[구조]` 0 으로 닫는다)

**게이트마다 종결 조건이 다르다.** Phase 2(계획·설계)는 **`[구조]` 지적 0** 으로 닫고, Phase 3(코드 검수)·Phase 4(PR 점검)는 종전대로 **무지적 3라운드**로 닫는다. 가른 근거는 이 절 맨 아래 "왜 갈랐나"에 실측으로 적었다.

#### 지적 분류 — 2축 + 부류 태그

- **`[설계|문서]` × 심각도(CRITICAL/HIGH/MEDIUM/LOW)** 를 리뷰어 프롬프트에서 요구한다. 설계 = 구현 행동·런타임 결과·테스트 그물·구현자를 오도하는 정본 규범을 바꾸는 것. 문서 = 문구·표식·명칭·참조 위치. **운영 지시를 오도하는 문서(롤백 절차·env 의미 등)는 문서라도 HIGH 이상으로 매긴다**(2026-09-02 `MTX_API_URL` 롤백 서술 실사고 — 운영자가 그 문장으로 롤백 판단을 내린다).
- **계획·설계 게이트(Phase 2)에서는 여기에 부류 태그를 하나 더 붙인다 — `[구조]` 또는 `[세부]`.** 부류 태그가 곧 Phase 2 의 종결 조건이라, 빠진 지적은 게이트가 닫혔는지 판정할 수 없다 — **태그 없는 지적은 반려하고 재분류시킨다.**
  - **`[구조]` = 되돌리기 비싼 결정.** 설계 정본 이탈 · 형상·축 선택(무엇을 동일성의 기준으로 삼는가) · 패키지·모듈 경계 · 이벤트 루프 점유 · **트랜잭션 소유**(경계를 어느 계층이 갖는가). 설계 단계를 넘겨 보내면 **며칠치 재작업**이 된다.
  - **`[세부]` = 코드에서 싸게 드러나는 것.** 구현 자리 · SQL 술어 · 반환값 · 좌표 · 문구 · 수치 · **트랜잭션 결속 자리**(어느 문장이 그 경계 안에 드는가). 코드 작성·실측(compose 등)·Phase 3 코드 리뷰가 계획 라운드보다 싸게 잡는다.
  - **갈리면 `[구조]` 로 올린다**(보수적으로 실패한다). 오케스트레이터가 리뷰어의 `[구조]` 를 `[세부]` 로 강등하려면 근거를 장부에 적는다 — 근거 없는 강등은 설계 결함을 "사실상 문서"로 강등해 닫는 것(2026-09-02 금지 조항)과 같은 부류의 위반이다.
- 설계/문서·구조/세부 **분류 근거를 통합 장부에 남긴다.**

#### Phase 2 (계획·설계 게이트) — 종결 = `[구조]` CRITICAL/HIGH 0

- **종결 조건: 같은 라운드에서 cc·cx 양측 동시에 `[구조]` CRITICAL/HIGH 0.** 교차 승인(cx 가 r1 에서, cc 가 r2 에서 각각 0)은 무효 — **한 라운드 안에서 동시에** 0이어야 한다.
- **`[세부]` HIGH 는 남아 있어도 게이트를 통과시킨다.** 대신 지우지 않는다 — 아래 세 개가 한 묶음이다:
  1. 통합 장부에 심각도·시나리오 **그대로** 싣는다.
  2. developer 브리핑에 **"착수 체크리스트"** 로 동봉한다.
  3. **Phase 3 코드 검수 프롬프트에 그 체크리스트를 넣어** 항목마다 닫혔는지 확인시킨다.
  3번이 빠지면 통과가 아니라 **유실**이다. 통과 보고에 체크리스트 항목 수를 적는다.
- **MEDIUM/LOW 는 지적이 아니라 "부수 관찰"이다** — 아래 프롬프트 규약대로 접는다.
- **라운드 상한 3회.** 진행 순서:
  1. **r1 — 전면 듀얼**: cc·cx **동시 발사**. 단독 발사는 위반이다(재검 라운드도 마찬가지).
  2. **처분**: 지적별로 수정 | 기록+사유 | 이연+귀속을 정해 **처분표**를 만든다.
  3. **확인 패스 1회**: 양측 **동시**. 입력은 **전문 재독이 아니라** ⓐ 처분표 ⓑ 바뀐 절만 ⓒ 회수 3항목·레퍼런스 3항목.
  4. 확인 패스에 **`[구조]` C/H 가 남아 있을 때만** 전면 라운드를 한 번 더 연다(→ r2, 다시 2·3번). 남지 않았으면 **확인 패스가 곧 종결**이다.
  - **상한은 전면 라운드 3회**(r1·r2·r3)를 뜻한다 — 각 전면 라운드에 딸린 확인 패스는 계수에 넣지 않는다. **넘으면 스스로 r4 를 열지 말고 kty 에게 회부한다.**
- **리뷰어 프롬프트는 CRITICAL/HIGH 만 지적으로 보고하게 한다.** MEDIUM/LOW 는 **"부수 관찰" 한 줄씩, 상한 10건**으로 접으라고 프롬프트에 명시한다. 오케스트레이터는 부수 관찰 중 고칠 것을 골라 처분하되 **라운드를 늘리지 않는다.**
- **싱글턴 교차 검증은 CRITICAL 만 건다**(부류 무관). 양측 판정이 **다 도착한 뒤** `[cc·cx]` 겹침을 가르고 남은 한쪽뿐인 것이 대상이다.
  - **싱글턴 HIGH 의 기본 처리는 "수용 수정 + 장부 기록"** 이다 — 고칠 것이면 반박시킬 이유가 없다.
  - **기각하려 할 때만** 교차 검증을 건다. 기각은 지적을 지우는 행위라 반대 진영의 반박이 필요하다 — **검증 없는 단독 기각은 Phase 2 에서도 금지**다.
  - 계약 전문(검증자·판정 4종·판정별 후처리)은 아래 "싱글턴 지적 교차 검증" 절을 따른다.
  - **산출물 이름도 Phase 3 과 같다** — `_workspace/verify-<원지적 출처>-<n>[-r<N>].md`(`NN_` 번호 접두어 금지 · `codex` 문자열 금지 · `00_design`/`01_plan` 접두어 금지). 아래 (9)B 의 예시가 Phase 3 파일만 들고 있지만 **이름 규약은 게이트 공통**이다.
- **재검 라운드의 리뷰어 입력은 처분표 + 변경된 절이다**(전문 재독 아님). **단 회수 3항목·레퍼런스 3항목은 매 라운드 유지한다** — 재검은 산출물이 수정된 뒤에 도는데 1라운드 검증은 옛 텍스트에 대한 것이라, 수정이 선행 결정과 새로 모순돼도 아무도 보지 않는 창이 생긴다(2026-08-17 감사: POK-79 r2·r3, POK-80 r6 에서 전량 탈락 실측 — 그 근거는 그대로다).

#### Phase 3 (코드 검수)·Phase 4 (PR 점검) — 현행 유지

- **무지적 라운드 = 같은 라운드에서 cc·cx 양측 동시에 설계 HIGH/CRITICAL 0 ∧ 문서 HIGH/CRITICAL 0.** 교차 승인(cx r3 승인·cc r4 승인 조합)은 무효.
- **설계 MEDIUM/LOW·문서 MEDIUM/LOW는 "고치고 기록"이다 — 반드시 처분(수정 소커밋 | 기록+사유 | 이연+귀속 트랙)하되 라운드를 무효화하지 않는다.** 다음 라운드가 수정분을 자연스럽게 재검한다. 근거: 이 부류는 실측상 전부 "지금은 안 터지지만 다음 변경에서 조용히 무너지는 자리"(테스트 그물 공백·잠복 오구성)였고 고치는 비용은 10~60줄인데, 라운드 무효화로 대응하면 종결이 보장되지 않는다(적대적 리뷰어에게 새 축을 주면 MED/LOW는 계속 나온다 — 2026-08-31에 한 번 폐기했던 이유와 같다).
- **종결 = 무지적 라운드 3회(연속 불요) ∧ 축 체크리스트 전부 커버.** 마지막 무지적 라운드에서 나온 MED/LOW 수정분은 **확인 패스 1회**(cc·cx **동시** — 입력은 수정 커밋 범위 한정 · CRITICAL/HIGH 만 차단)로 닫는다 — 새 축을 파는 전면 라운드를 다시 열지 않는다. **의도적으로 한쪽만 발사하는 확인은 없다** — 확인 패스, 미니 확인(수정분 몇 줄만 보는 좁은 확인), 게시 직전 검토(외부 게시 바로 앞의 1회 검토)도 같은 메시지로 동시 발사한다. 예외는 둘뿐이다: codex 호출이 실패하면 위 "듀얼 리뷰 규칙"의 실패 대체 조항(Claude 단독 진행 · 보고에 "듀얼 리뷰 생략(codex 실패)" 명시)을 따르고, 싱글턴 교차 검증은 아래 그 절(반대 진영 축소 dispatch)을 따른다(2026-09-26 kty "무조건 듀얼리뷰지": 이 줄의 옛 문구 "cc 단독 또는 codex 축소 입력"을 근거로 오케스트레이터가 한쪽 리뷰어만 돌리겠다고 보고한 실사고 뒤 폐기).
- **축 체크리스트를 라운드 전에 정한다**(프로젝트별로 계획 게이트 장부에서 도출 — 예: 트랜잭션 형상 · 상태 결정 · 폴백 판정 · 관측 폴러 · 업로더 축 · 기동/취소·동시성 · 경계 임포트 · compose/CI · 오류 경로·재시도 사다리 · 시간 산술·정규식·config 경계 · 문서↔코드 · **관측 신호 등급·필터 대칭**(set/clear 가 같은 레벨인가 — 2026-09-03 PR #153 실측: 게이지 clear 만 Info 라 `LOG_LEVEL=warn` 에서 걸러졌는데 cc·cx 어느 쪽 축에도 없어 통과했고 claude[bot]이 잡았다) · **티켓 범위·오버엔지니어링** · 불변식). "깨끗함"은 리뷰어의 선택이 아니라 체크리스트 커버로 정의한다. **Phase 3·4 의 라운드가 5회를 넘으면 kty 에게 회부한다** — Phase 2 의 상한은 위 전면 라운드 3회이고, 이 5회는 Phase 2 로 내려오지 않는다.
- **싱글턴 CRITICAL/HIGH 교차 검증(아래 절)은 생략 불가** — "수용해서 고치면 안전하니 생략"·"계획 문언으로 오케스트레이터가 단독 반려" 둘 다 위반이다(2026-09-02 실사고 3건 — 사후 verify 기록으로 보정). 문서 HIGH도 대상이다. Phase 2 의 CRITICAL 한정 축소는 **Phase 2 에만** 적용되며 여기로 내려오지 않는다.
- Phase 2 에서 넘어온 **`[세부]` HIGH 착수 체크리스트**를 검수 프롬프트에 넣어 항목별 닫힘을 확인한다(위 Phase 2 규약 3번). 닫히지 않은 항목은 그 라운드의 지적으로 세운다.

#### 적용 단위 — 계획 게이트는 개발 전 한 번, 무지적 3라운드는 PR 전체에서 (2026-09-29 kty 확정)

한 PR 을 여러 커밋으로 나눠 개발할 때 위 규약을 **커밋마다** 되풀이하지 않는다. 리뷰를 몰아서 돌리는 자리는 둘이다 — 개발 전의 계획 게이트(Phase 2)와 PR 직전의 종결 라운드(Phase 3 의 끝이다 — 그 뒤 Phase 4 점검은 위 규약대로 따로 돈다).

- **계획서는 개발 도중 커밋마다 코드에 맞춰 고치지 않는다.** 계획은 Phase 2 에서 한 번 리뷰받고 닫는다. 개발하면서 드러난 편차(계획과 다르게 구현한 자리 · 계획이 비워 둔 자리를 채운 판단 · developer 가 막혀 `ecc:planner` 조정을 받은 것)는 진행 기록과 통합 장부에 적고, 그 커밋의 검수 프롬프트에 넣는다(커밋별 작업 지시를 쓰는 프로젝트면 거기에도). 계획서와 운영 문서(README 등)는 종결 라운드 전에 한 번 코드에 맞추고 종결 라운드가 함께 본다. PR 본문은 Phase 4 에서 pr-author 가 쓰고 pr-reviewer 가 본다.
  - 커밋별 작업 지시·체크리스트를 새로 쓰거나 고치는 일도 계획 게이트를 다시 열지 않는다 — 그 대조는 그 커밋의 검수 라운드가 본다. 커밋별 작업 지시 파일에는 `NN_plan` · `NN_design` 앵커 이름을 쓰지 않는다(그 이름은 계획 게이트의 주산출물 전용이다).
  - 예외: 편차가 `[구조]` 부류(되돌리기 비싼 결정 — 위 "지적 분류")면 그 자리에서 멈추고 사용자에게 회부한다. 계획 게이트를 다시 열지는 사용자가 정한다. `[세부]` 편차로는 계획 게이트를 다시 열지 않는다.
- **커밋별 검수는 듀얼 1라운드다.** Phase 3 의 1–8 을 커밋마다 한 번 돈다 — cc·cx 동시 1라운드(보안 트리거에 닿으면 보안 검수 병렬) → **CRITICAL/HIGH 만 고친다** → 고친 것이 있으면 수정분 확인 패스(cc·cx 동시 · CRITICAL/HIGH 만 차단) → 커밋 → 기능 브랜치로 push(커밋이 원격에 없으면 종료 훅이 턴 종료를 막는다). 싱글턴 교차 검증·라운드 보고·변경 설명·완료 감사는 그대로다.
  - 확인 패스에도 CRITICAL/HIGH 가 남으면 고치고 한 번 더 확인한다. **두 번째 확인에도 남으면 더 돌리지 말고 사용자에게 회부한다.**
  - MEDIUM/LOW 는 처분을 "이연 + 귀속(PR 단계)"으로 적어 두고 커밋을 막지 않는다. 종결 라운드 전에 한꺼번에 처분하고(수정 | 기록+사유 | 이연+귀속 — 위 규약), 이연 목록을 종결 라운드 1회차 프롬프트에 넣어 처분을 확인시킨다.
  - Phase 2 에서 넘어온 `[세부]` HIGH 착수 체크리스트는 항목을 맡은 커밋의 라운드 프롬프트에 넣어 닫힘을 보고, 종결 라운드 프롬프트에 전체 목록을 다시 넣는다(앞 커밋에서 닫힌 항목이 뒤 커밋에서 되살아났는지).
  - 커밋별 라운드의 보고에는 무지적 계수 대신 "계수 비대상(커밋 N)"을 적는다.
- **종결 = PR 전체를 입력으로 한 라운드에서 무지적 3회 ∧ 축 체크리스트 전부 커버.** 입력은 셋이다 — 기준 브랜치를 먼저 동기화한 뒤의 PR 전체 차분(커밋 하나의 차분이 아니다) · 현재 계획서(`_workspace/` 의 계획서는 저장소 밖이라 차분에 없다) · 차분에 들지 않은 운영 문서의 목록. 셋을 cc·cx 프롬프트에 함께 넣는다. 라운드 상한 5회는 종결 라운드에만 센다 — 커밋별 라운드와 그 확인 패스는 상한에도 무지적 계수에도 넣지 않는다. 확인 패스·싱글턴 교차 검증은 위 규약 그대로다.
  - 종결 라운드에서 나온 CRITICAL/HIGH 는 앞 커밋을 고쳐 쓰지 않고 그 위에 수정 커밋을 얹어 고친다.
- **커밋이 하나뿐인 PR** 은 커밋별 라운드를 따로 열지 않는다 — 첫 종결 라운드가 그것을 겸하고, PR 전체의 무지적 3회로 닫는다.
- **이미 진행 중인 PR** 은 이 규약을 다음 커밋부터 적용한다 — 앞 커밋의 검수를 다시 열지 않는다.

**왜 (2026-09-29 실측):** 이 규약은 적용 단위를 말하지 않았고 같은 프로젝트의 두 PR 이 서로 다르게 읽었다. 앞 PR(커밋 7개)은 커밋마다 1라운드를 돌려 그 라운드를 무지적 계수에 넣고, PR 전체 diff 종결 라운드를 한 번 돌아 약 30시간에 닫았다. 다음 PR(커밋 9개)은 커밋마다 무지적 3회를 채우고 커밋이 끝날 때마다 계획서를 코드에 맞춰 다시 듀얼 리뷰했다 — 착수 뒤 커밋 넷까지 약 88시간이 지났다(결정 대기 약 28시간 포함 · 일한 약 60시간 가운데 코드 개발·검수 27 · 계획 라운드 20 — 어림). 새 규약은 커밋 단계를 앞 PR 처럼 가볍게 하고 끝은 그보다 무겁게 한다 — 종결의 무지적 3회를 전부 PR 전체로 채운다. 치르는 값은 결정 기록(ADR-0025)의 Consequences 에 적었다 — 커밋 단계에서 놓친 결함이 끝에서 드러나고, 이연한 MEDIUM/LOW 가 PR 끝에 몰리고, 종결 라운드의 입력이 크다.

#### 공통 운영 규약

- **codex 판정 확인 절차**: 백그라운드 codex는 **완료 통지 뒤 파일 말미(tail)에서** `### 최종 판정` 헤더를 읽는다. 실행 중 파일을 조기 확인하거나, 프롬프트 안에 쓴 "usage limit" 문자열을 grep한 것을 실패로 오독하지 않는다(2026-09-02 실사고 — 완주한 무지적 라운드를 "무판정"으로 기록·전파). 실패는 `ERROR:` 접두 줄로만 판정한다. **소모 절감**: 비테스트 diff를 `git diff … > _workspace/NN_diff_nontest.patch`로 뽑아 주 입력으로 지정한다(실측 전체 탐색 416k~460k 토큰 → 파일 입력 208k~290k — effort high 때 실측이라 xhigh 는 더 든다).
- **지적 수정은 인스턴스가 아니라 부류를 닫고 증거를 남긴다**(2026-09-02 kty 확정): 리뷰 지적을 고칠 때 그 문장·그 분기만 고치지 말고 같은 부류를 닫는다 — 경계 검증은 파싱 결과 필드 패치가 아니라 원칙 규칙(예: 원문에 금지 문자가 있으면 거부)으로, 문서 오서술은 지적된 문장만이 아니라 같은 의미의 서술을 전수 grep해 0건으로, 새로 넣는 방어 가드는 직접 단위 테스트(뮤테이션 재적용 시 FAIL)와 함께. 수정 커밋 메시지나 progress에 그 증거(grep 범위·0건 / 테스트 이름)를 남긴다. 실측: POK-195 M3 r4 수정 3건이 전부 인스턴스 수정이라 r5에서 같은 자리 3곳이 재발했고 r5 지적 6건 중 3건이 r4 수정의 자식이었다. 다음 라운드 프롬프트에는 "각 수정이 부류를 닫았는가, 같은 부류가 다른 파일에 남았는가"를 명시 조건으로 넣는다.

#### 왜 갈랐나 (2026-09-04 실측 — POK-195 M4 계획 게이트)

계획 듀얼 리뷰를 r1~r6 까지 돌린 결과다. **6라운드 × 리뷰어 2 × 약 30만 토큰 + 싱글턴 교차 검증 ≈ 500만 토큰.**

- **r2~r4 의 CRITICAL/HIGH 는 구조 부류였다** — 동일성 축 선택 · 발행이 이벤트 루프를 막음 · 계수 이중 가산 · 동적 경로에 슬레이트 불가. **설계 단계가 아니면 며칠치 재작업**이 되는 것들이라, 계획 라운드가 값을 했다.
- **r5~r6 의 HIGH 는 구현 세부 부류였다** — 어느 SQL · 어느 자리 · 트랜잭션 결속 · 캐시 갱신 자리. **6건 중 4건은 코드 작성·compose 실측·코드 리뷰가 더 싸게 잡는다.**

**결론: HIGH 의 성격이 구현 세부로 내려오면 계획 라운드를 멈추는 게 토큰당 효율이 높다.** 무지적 3라운드는 diff 가 실재하는 코드·PR 단계에 남기고, 계획·설계 단계는 `[구조]` 0 으로 닫는다.

### 싱글턴 지적 교차 검증 (2026-08-15 사용자 확정 · 2026-09-04 범위 개정 — Phase 2·3 적용)

한 진영만 잡은 CRITICAL/HIGH 를 그대로 믿으면 위양성(false positive — 실제로는 결함이 아닌 지적) 때문에 개발이 헛돌고, 오케스트레이터 재량으로 단독 기각하면 진짜 CRITICAL 이 조용히 사라진다. 그래서 **기각하기 전에 반대 진영이 한 번 반박해 보게** 한다.

(1) **트리거:** 심각도 CRITICAL/HIGH 이면서 출처가 `[cc]` 또는 `[cx]` **한쪽뿐**인 지적. `[cc·cx]`(양쪽이 잡음)와 MEDIUM 이하는 대상이 아니다. `ecc:security-reviewer`·`[tq]` 지적도 제외한다 — 판정 축이 다르고(통과/차단·테스트 품질), 그 축에는 대응하는 반대 진영이 정의돼 있지 않다.

(2) **적용 범위: Phase 2(계획·설계) = CRITICAL 만 · Phase 3(코드 검수) = CRITICAL/HIGH 전부 · Phase 4(PR 점검) = 비대상.** 범위의 정본은 위 "종결 기준·라운드 규약"이다. (2026-09-04 개정 — 그전 원문은 "Phase 3 만"이었으나 2026-09-03 kty 확정으로 계획 게이트에 이미 적용되고 있어 **원문이 실태와 어긋난 채로 세션들이 돌았다.** 그 틈을 닫는다.) Phase 2 에는 diff 가 없으므로 **재현 대상이 코드가 아니라 설계서·계획서 본문과 선행 결정 정본**이다 — 파일:라인 근거 요구는 그대로이고 가리키는 대상만 바뀐다. Phase 2 의 싱글턴 HIGH 는 이 절차 대신 "수용 수정 + 장부 기록"이 기본이고 **기각하려 할 때만** 건다. 심각도 규칙(위 — 출처 무관 동일)은 **그대로**다. 더하는 것은 차단을 확정하기 전의 재현 확인 절차뿐이다.

(3) **검증자 = 반대 진영:** `[cc]` 단독이면 codex(위 명령 줄 그대로 — 모델·effort 임의 하향 금지), `[cx]` 단독이면 `ecc:code-reviewer` 를 **새 컨텍스트로 축소 dispatch** 한다.
  - 공통 계약 4종(위 "외부(ECC) 참조 에이전트 dispatch 계약")은 승계한다 — ① 한국어 ② 프로필·principles.md 기준 ③ 산출물은 응답 본문, 파일 저장은 오케스트레이터 ④ 확인 못 한 항목은 "미확인".
  - 검수 전면 계약 ①~⑥·⑧(판정 줄 형식·카테고리 태그·타입체크 재실행·TDD 표명 확인·경계면 전수·변경 범위 판정)은 **승계하지 않는다.** ⑦(수정 금지 — 관찰·판정만)만 승계한다.
  - 임무는 **지정된 단일 지적 하나의 반박**이다. 전면 재검수 금지, 새 지적 생성 금지(부수 관찰은 "부수 관찰"로 분리해 보고 — 검증이 검증을 낳는 재귀를 막는다).
  - ECC 부재 폴백: 동명 전역 에이전트(`~/.claude/agents/`) → 그것도 없으면 오케스트레이터가 직접 수행하되 산출물에 "ECC 미설치 — 오케스트레이터 대체 수행(독립 컨텍스트 아님)"을 명시한다. 반대 진영이라는 성격은 성립하지만 같은 세션의 앵커링은 남는다.

(4) **임무:** "이 지적을 반박하라" — 지적의 시나리오를 실제 코드에서 추적한다. 토의 없음, 반론 라운드 없음, **1회 판정.** 반증 근거는 파일:라인이 필수다 — 근거 없는 "문제 없어 보임"은 반박이 아니라 `미확정` 이다.

(5) **판정 — 개념은 3분기, 라벨은 4종:**

| 라벨 | 뜻 | 후처리 |
|---|---|---|
| 재현됨 | 원 시나리오 재현 & 영향 CRITICAL/HIGH 유지 | 차단 확정 → developer 되돌림 |
| 반박 성공-현상 부재 | 시나리오 불성립 | 완전 기각. 통합 산출물에 `기각(<verify 경로>)` 표시, 차단에서 제외 |
| 반박 성공-심각도 강등 | 현상은 재현되나 영향이 MEDIUM 이하 | 지우지 않는다 — MEDIUM 으로 보존하고 기존 MEDIUM 처리. 차단 아님·되돌림 없음 |
| 미확정 | 재현도 반증도 못 함 | 사용자 보고의 🔀 결정 필요로 승격 |

(6) **미확정의 출구:** 사용자가 판단을 위임하면 보수적으로 `재현됨` 취급해 되돌린다 — 위양성 1건의 비용이 CRITICAL 1건 누락의 비용보다 싸다(이 판단 근거를 verify 산출물에 적는다). 승격 대기 중에 병행 수정으로 대상 코드가 바뀌면 옛 판정은 무효이고 새 라운드로 재검증한다(옛 파일은 지우지 않고 보존).

(7) **검증 dispatch 가 안 되는 두 경우 — 결과가 다르다:**
  - **규칙 미발동:** codex 듀얼 리뷰 자체가 없던 턴(`[cx]` 부재 → 트리거의 전건이 거짓). 이때는 "듀얼 리뷰 생략(codex 실패)"과 함께 **"싱글턴 검증도 미발동"**을 보고에 명시한다.
  - **검증 실패:** 듀얼 리뷰는 성공했고 검증 호출만 실패. 일반 에러 규칙(아래 "에러 핸들링")의 적용을 받되 **"결과 없이 진행"의 그 결과 자리가 `미확정`** 이다 — 1회 재시도 후에도 실패면 `미확정` 으로 확정하고 사용자에게 승격한다. 누락을 명시했다는 사실이 진행 허가가 되지 않는다.

(8) **기각 기록의 재사용 조건:** 이전 라운드의 기각(`verify-*.md`)을 다시 인용하려면 **검증 시점의 의존 파일 내용이 그대로**여야 한다.
  - 검증자는 시나리오가 의존하는 파일 전체(반증 근거 파일 + 시나리오 경로에 등장하는 파일 — 교차 파일 포함)를 verify 산출물의 `의존 파일:` 블록에 `<경로>\t<해시>` 로 기록한다. 해시는 워킹트리 내용 기준(`git hash-object -- <파일>`).
  - 재사용 조건은 **그 집합 전체의 해시 동일**이다. 하나라도 다르거나 파일이 사라졌으면 새 지적으로 재검증한다.
  - 커밋 간 diff(`git diff <검증HEAD>..HEAD`)로 판정하지 않는다 — Phase 3 의 수정은 아직 커밋되지 않아(커밋은 Phase 4) 가드가 걸려야 할 상황에서 항상 빈 출력이 된다.
  - **재확인을 누가 하나:** 원칙은 반대 진영 재dispatch 다. **해시 불일치로 촉발된 재확인에 한해** 원 지적자의 자기 재검토를 **선행 트리아지**(본 검증 앞의 1차 분류)로 허용한다 — 단 **기각 유지 방향만 자기 확정할 수 있고**, 철회든 유지든 근거를 파일:라인으로 새 verify(라운드를 올린 파일)에 기록해야 성립한다. **지적을 되살리는 방향이면 자기 판단으로 확정하지 않고**, 그 지적을 새 라운드의 싱글턴으로 세워 반대 진영에 재검증시킨다. 근거 없는 판단은 재확인이 아니다.

(9) **산출물 (이름·머리 형식이 계약이다):**

  **A. 검수 통합 산출물 — `_workspace/phase3-review.md`** (라운드는 `phase3-review-r2.md` …)
  - **`NN_` 번호 접두어를 붙이지 않는다 — 이 이름 그대로 저장한다.** 기존 명명 관행의 예외임을 계약으로 못박는다(pr-reviewer 의 대조와 grep 검증이 정확 일치로 단순해진다. 와일드카드 허용형은 자리마다 표현이 흔들려 드리프트를 부른다).
  - `codex` 문자열 금지(위 명명 계약) / `00_design`·`01_plan` 접두어 금지(머리 표명 게이트 재귀 방지). `phase3-` 접두어가 Phase 2 리뷰 산출물과 기계적으로 구분한다.
  - **동봉·대조 대상은 최신 라운드 하나다**(이전 라운드 파일은 보존되지만 pr-author 입력·pr-reviewer 대조 기준이 아니다).
  - 머리 3줄 고정:
```
Phase 3 최종 판정: 통과|보류
원 리뷰: [cc] <경로> · [cx] <경로|없음(<사유>)> · [보안] <경로|없음(비대상)> · [tq] <경로|없음(비대상)>
라운드: r<N>
```
  없는 항목은 지우지 말고 `없음(<사유>)` 로 남긴다 — 빈칸과 "없음"은 다르다(예: `[cx] 없음(codex 호출 실패)`). 이어서 지적 목록(일련번호·출처 태그·심각도·시나리오·처리 결과)을 싣는다. 생성 주체는 오케스트레이터다(공통 계약 ③).
  - **생성 시점:** Phase 3 의 검증(6번) **직전**에 잠정 `Phase 3 최종 판정: 보류` 로 만들어 둔다(검증자가 `원지적:` 으로 가리킬 주소가 dispatch 시점에 이미 있어야 한다). 최종 판정은 7번에서 이 줄을 갱신해 확정한다.
  - **이름 확인의 주체·시점:** 저장한 **직후** 오케스트레이터가 `ls _workspace/` 로 두 산출물의 실제 파일명에 `NN_` 접두어가 붙지 않았는지 본다 — 기존 관행이 손에 배어 있어 미끄러지기 쉽고, 이름이 어긋나면 pr-reviewer 의 대조가 조용히 빈손이 된다.

  **B. 검증 산출물 — `_workspace/verify-<원지적 출처>-<n>[-r<N>].md`** (번호 접두어 금지·`codex` 금지·`00_design`/`01_plan` 접두어 금지)
  - `<n>` 은 그 라운드 `phase3-review` 파일의 지적 일련번호, `-r<N>` 은 통합 산출물과 같은 라운드 번호다(`verify-cc-3-r2.md` = `phase3-review-r2.md` 의 3번 `[cc]` 지적). 이 기준은 여기 한 번만 적는다 — 규칙이지 데이터가 아니므로 파일 머리에 반복하지 않는다.
  - 덮어쓰지 않는다 — 같은 이름이 이미 있으면 라운드를 올린다.
  - 머리 6개 필드. 5번째 `의존 파일:` 은 가변 길이 블록이고, 블록은 다음 필드인 `판정:` 줄에서 끝난다:
```
원지적: _workspace/phase3-review[-rN].md #<n>
요약: <한 줄>
검증자: codex(read-only) | ecc:code-reviewer(축소 계약) | 오케스트레이터 대체(독립 컨텍스트 아님) | 원 지적자 자기 재검토(해시 불일치 재확인 한정)
검증 시점 HEAD: <커밋 해시>
의존 파일:
  <경로>	<해시>
  <경로>	<해시>
판정: 재현됨 | 반박 성공-현상 부재 | 반박 성공-심각도 강등 | 미확정
```
  - `의존 파일:` 블록이 비어 있으면 그 기각 기록은 재사용하지 않는다(항상 재검증 — 안전한 쪽으로 실패한다).

  **C. 여러 커밋으로 나눠 개발하는 PR 의 커밋별 산출물** — 통합 `_workspace/phase3-review-c<N>-r<M>.md` · 검증 `_workspace/verify-<원지적 출처>-<n>-c<N>-r<M>.md`(`<N>` = 커밋 번호 · `<M>` = 그 커밋 안의 라운드 번호 · 머리 형식과 금지 규칙은 A·B 와 같다). 여러 커밋으로 나눠 개발하는 PR 의 Phase 3 에서는 A·B 의 이름을 종결 라운드 산출물에만 쓴다 — pr-author 의 입력과 pr-reviewer 의 대조 기준은 종결 라운드의 A 이고, 커밋별 산출물은 그 입력에서 뺀다("종결 기준·라운드 규약"의 "적용 단위" 절).

(10) 건수 상한은 두지 않는다(YAGNI). 여러 건이면 병렬 dispatch 한다.

## 사용자 보고 블록 규칙 (2026-08-01 사용자 확정)

**사용자에게 내는 모든 보고·산출물 안내(Phase 전환 보고, 설계/계획 제시, 검수 결과, PR 안내, 완료 보고)는 맨 위에 이 블록을 붙인다:**

```
📌 읽어야 할 것 (3줄 이내): <이번 보고에서 사용자가 책임지는 핵심만>
🔀 결정 필요 (N건): <사용자만 답할 수 있는 것. 없으면 "없음">
📦 나머지는 아카이브: <어디에 저장돼 있고, 언제 다시 보면 되는지 한 줄>
```

- 근거: 이해 부채(comprehension debt) 대응 — 사용자는 전체가 아니라 ①결정 ②검증 증거 ③한계만 읽는다. 상세는 `_workspace/`가 보존하고, 문제가 생겼을 때 역추적한다.
- 본문 **서식**은 `google-styleguide` 스킬의 마크다운 규칙(`docguide-style.md`)을, 그 위에 **문장 품질**은 readable-writing 스킬(용어 즉석 괄호 풀이 포함)을 따른다. 충돌하면 Google 이 이긴다(principles.md '스타일 정본' 절).

## Phase 1: 명료화 게이트 (clarifier)

**항상 먼저** `clarifier`로 요청의 모호점·비가역 작업·숨은 가정을 점검한다.
- clarifier 는 질문을 만들기 **전에** 프로필 9절 진입점에서 선행 결정을 회수한다(ADR-0013 ②) — 과거 결정으로 답이 되는 질문은 사용자에게 보내지 않고 그 결정을 인용한다. 질문이 소음이 되면 진짜 질문도 무시된다. 출력의 `사전 결정 회수:` 줄로 표명한다(산문 검증뿐 — 기계 게이트 대상 아님).
- 판정 "확인 필요" → 정리된 질문을 **AskUserQuestion으로 사용자에게 직접** 묻는다(clarifier는 질문을 만들 뿐, 실제 묻기는 오케스트레이터가). 답을 받고 진행.
- clarifier 질문·사용자 답변은 오케스트레이터가 `_workspace/00_clarifier_qa.md`에 저장한다 — 재실행 시 clarifier가 읽고 이미 답변된 것은 다시 묻지 않는다. **판정이 "명확"(질문 0건)이어도 이 파일을 항상 저장한다** — 판정과 `사전 결정 회수:` 표명을 기록한다. "저장할 질문이 없다"는 해석이 파일 부재를 낳고, 부재는 clarifier 층의 사후 검증을 불가능하게 한다(2026-08-17 감사: POK-79 실측). Phase 2 이후 파이프라인 중 발생한 사용자 문답도 이 파일에 이어 적는다. completion-auditor 가 파일 실존을 상비 점검한다.
- 판정 "명확" → Phase 2로.

> 이 게이트가 이 하네스의 1번 가치다. "확실하지 않으면 추측 말고 물어본다"를 파이프라인이 강제한다.

## Phase 2: 설계·계획↔검증 루프 (ecc:architect → ecc:planner ⇄ plan-reviewer)

**구조적 변경 판별(오케스트레이터):** 새 모듈/레이어 신설 · 기존 경계나 데이터모델 변경 · 3개 이상 모듈 영향 중 하나라도 해당하면 "구조적".

**레퍼런스 조사 단계 (ADR-0015 — Phase 2 진입 시, 구조적/비구조적 공통):**
0. **조사 필요 판단(오케스트레이터 — 기계 불가, 산문 판단):** 이번 작업의 설계 결정이 조직 밖에 공개된 선례·경쟁 구현·실패 사례에 따라 달라질 수 있는가. 순수 내부 리팩터링·버그픽스·자기참조 작업은 대개 불요다 — 전 작업 기본 조사가 아니다("조사가 필요하다고 판단되는 지시사항에 대해서만"). 비용: 조사 1회 = 에이전트 2 dispatch(각 수 분·상당 토큰).
   - **필요 판단 시:** `research-collector` dispatch(주제 = 작업 요약 + 아래 인접 도메인 지시) → `research-evaluator` dispatch → 평가 채택분을 architect·planner 프롬프트에 주입. evaluator 의 "재수집 필요"는 1회만 수용, 그 뒤에도 미달이면 실패로 접는다. 채택 0건이면 그 사실 자체를 주입한다("찾아봤지만 쓸 만한 것이 없더라"도 조사의 결과다 — `조사함(<시도 범위> — 채택 0건, 평가: <경로>)`).
   - **인접 도메인 지시(조사 프롬프트에 상수로 포함):** "대상 도메인과 정확히 일치하는 사례만 찾지 마라. 인접 도메인 — 같은 문제를 다른 제약에서 푼 시스템 — 을 포함하라. 우리가 라이브 스트리밍이면 VOD·저장·CDN 도 본다."
   - **불요 판단 시:** 불요 사유를 dispatch 프롬프트에 명시 — 작성자가 승계하거나 뒤집어 "레퍼런스 조사 필요"를 반환할 수 있다(재dispatch 1회).
   - **실행 실패 시(도구 장애·에이전트 2회 실패):** 기존 에러 규칙("결과 없이 진행하되 누락 명시")의 적용을 받되 **표명이 그 명시 자리다** — 작성자가 `실패(<시도 — 사유>)` 로 표명하고 사용자 보고에도 올린다. research 에이전트 미설치면 오케스트레이터가 직접 대체 조사(WebSearch 등)하되 "research 에이전트 미설치 — 대체 수행" 명시, 대체도 불가하면 실패 경로.
   - **검수가 "조사 재시도 필요"로 보류하면** 되돌림 대상은 작성자가 아니라 **이 조사 단계**다(작성자는 조사 dispatch 를 못 한다). 조사 사이클 총 상한 2회 — 소진 후에도 보류면 사용자 보고의 "결정 필요"로 승격.

**구조적 변경이면 (2-pass):**
1. `ecc:architect`를 dispatch 계약대로 호출해 설계서를 받는다 — 모듈 경계·계약·패턴·대안 트레이드오프. 오케스트레이터가 `_workspace/00_design.md`에 저장.
   **머리 두 줄을 확인한다** — 첫 줄 `사전 결정 회수:` 와 둘째 줄 `레퍼런스 조사:` 가 없으면 해당 단계를 건너뛴 것이므로 되돌린다. 이 형식은 Stop 훅(`stop:retrieval`, ADR-0013·0015)도 기계로 검사한다 — 형식이 어긋난 산출물이 저장된 턴은 고치기 전엔 끝나지 않고, 지키면 게이트가 스스로 풀린다. 진짜 읽었는지·조사했는지는 여전히 기계가 못 본다 — 그건 plan-reviewer·codex 의 회수·레퍼런스 검증 각 3항목(산문 계약)이 본다.
2. `plan-reviewer` **1차 pass(설계만)**: 제0원칙·계약 명시성·불변식 충돌·과설계를 검증. 보류면 ecc:architect로 루프 — 단 보류 사유가 조사 재시도이면 위 조사 단계로, `principles 미주입(dispatch 결함)` 이면 작성자 되돌림 없이 주입을 고쳐 같은 pass 를 재dispatch.
3. `ecc:planner`가 설계서를 입력으로 구현 계획서를 작성. 오케스트레이터가 `_workspace/01_plan.md`에 저장.
4. `plan-reviewer` **2차 pass(계획+정합성)**: 기존 점검 전체 + 설계↔계획 정합성. 보류면 ecc:planner로 루프 — 단 보류 사유가 조사 재시도이면 위 조사 단계로, `principles 미주입(dispatch 결함)` 이면 주입을 고쳐 같은 pass 를 재dispatch.

**비구조적이면 (기존 흐름):**
1. `ecc:planner`로 구현 계획서를 만든다. 영향 범위·모듈 경계(제0원칙)·PR 단위 단계·리스크·테스트 계획. 오케스트레이터가 `_workspace/01_plan.md`에 저장.
2. `plan-reviewer`가 완결성·영향범위 정확성·PR 단위·리스크 누락·테스트 구체성·아키텍처 정합(4절)·제0원칙을 검증.
3. 보류(차단)면 ecc:planner로 되돌려 수정 → 재검증. **승인까지 루프.** 단 보류 사유가 조사 재시도이면 위 레퍼런스 조사 단계로, `principles 미주입(dispatch 결함)` 이면 주입을 고쳐 재검증만 다시 dispatch.

> 계획에도 generate-verify를 두는 이유: 결함은 늦게 잡을수록 비싸다. 가장 싼 지점(구조적이면 설계 직후)에서 결함을 잡는다. plan-reviewer는 pass마다 새 컨텍스트로 단일 임무만 받으므로 혼란이 없다.

**계획 게이트가 닫힌 뒤(여러 커밋으로 나눠 개발하는 PR):** 개발 도중에는 계획서를 커밋마다 고쳐 다시 리뷰하지 않는다 — 편차는 진행 기록과 통합 장부에 적고, 계획서는 종결 라운드 전에 한 번 코드에 맞춘다("종결 기준·라운드 규약"의 "적용 단위" 절).

## Phase 3: 개발↔검수 루프 (developer ⇄ ecc:code-reviewer)

1. `developer`가 계획대로 구현, 프로필 3절 타입체크+테스트를 통과시킴. 출력 마지막에 `방법론: superpowers:test-driven-development 따름` 줄이 **있는지 확인** — 없으면 미준수로 되돌린다.
2. `ecc:code-reviewer`가(dispatch 계약대로 — 판정 줄·심각도·시나리오·카테고리 태그) 경계면 정합성(5절)·실패 시나리오·불변식 위반(4절)·제0원칙·테스트를 검수.
3. **보안 트리거 판별:** 변경이 인증/인가·사용자 입력·DB 쿼리·파일시스템·외부 API·암호화·결제·시크릿에 닿으면 `ecc:security-reviewer`를 검수와 **병렬** dispatch. CRITICAL = 병합 차단. 산출물은 오케스트레이터가 `_workspace/security-review.md`에 저장한다 — pr-reviewer가 "보안 검수 이행" 점검 시 이 파일을 확인한다.
4. **듀얼 리뷰:** 같은 diff를 위 "듀얼 리뷰 규칙"대로 Codex에 병렬 리뷰시킨다 (모델·태그·차단 규칙은 공통 규칙 참조).
5. **테스트 품질 리뷰 (조건부):** 새 기능·버그수정처럼 테스트가 핵심 방어선인 변경이거나 검수가 테스트 품질에 의문을 표하면, `ecc:pr-test-analyzer` 에이전트를 병렬 dispatch — 행동 커버리지 관점("이 테스트가 진짜 버그를 잡는가", assert 없는 테스트·mock 범벅·커버리지 숫자 놀음 적발). 지적은 **`[tq]`** 태그로 통합. 신규 에이전트를 만들지 않고 ECC 참조를 쓰는 이유: 만들기 전에 찾는다(레이어 원칙).
6. **싱글턴 지적 교차 검증** (통합 산출물을 잠정 `보류` 로 저장한 뒤 — 지적 통합 직후·되돌리기 전. 계약 전문은 위 "싱글턴 지적 교차 검증" 절): 통합된 지적 중 **CRITICAL/HIGH 이면서 출처가 `[cc]`·`[cx]` 한쪽뿐**인 것(보안·`[tq]` 제외)을 목록으로 뽑아 계약대로 반대 진영에 병렬 dispatch 하고, 각 검증 결과를 `_workspace/verify-<원지적 출처>-<n>[-r<N>].md` 에 저장한다. 판정별 처리는 그 절 (5) 표와 같다 — **재현됨** → 차단 확정, developer 되돌림 / **반박 성공-현상 부재** → 완전 기각, 통합 산출물에 `기각(<verify 경로>)` 기록 / **반박 성공-심각도 강등** → MEDIUM 으로 보존(차단 아님·되돌림 없음) / **미확정** → 사용자 보고의 🔀 결정 필요로 승격. 검증하지 않은 싱글턴 지적은 기각도 무시도 아닌 **미처리**다 — 미처리를 남긴 채 다음 단계로 갈 수 없다.
7. **Phase 3 최종 판정 통합:** 오케스트레이터가 원 검수·codex·보안·`[tq]`·싱글턴 검증 결과를 모두 반영해 판정을 확정하고, `_workspace/phase3-review[-rN].md` 첫 줄을 `Phase 3 최종 판정: 통과/보류` 로 **갱신해 확정한다**(파일은 6번 직전에 잠정 `보류` 로 이미 생성돼 있다). 원 리뷰어의 판정 줄은 **입력**이다 — 반박 성공으로 차단 지적이 사라졌다면 원 판정이 '보류'여도 최종은 '통과'일 수 있고, 그 경우 어느 지적이 어느 verify 로 기각·강등됐는지 병기한다. 이 파일이 pr-author 의 입력이자 pr-reviewer 의 대조 기준이다.
8. 보류(CRITICAL/HIGH — cc·cx·ecc:security-reviewer·tq 어느 쪽이든. **단 싱글턴 지적은 6번 검증에서 `재현됨` 으로 확정된 것만 해당**)면 developer로 되돌려 수정 → 재검수. **통과까지 루프.** *(재검수 라운드마다 새 phase3-review-r<N> — (9)A)*
9. 3절이 런타임/브라우저 관찰을 요구하면 실제 동작 확인까지.

**여러 커밋으로 나눠 개발하는 PR:** 위 1–8 을 커밋마다 한 번 돈다 — 8번의 재검수는 전면 라운드가 아니라 수정분 확인 패스로 돌고(CRITICAL/HIGH 가 남으면 한 번 더 · 그래도 남으면 사용자 회부), MEDIUM/LOW 는 이연해 PR 단계에서 처분한다. 커밋은 첫 커밋 전에 프로필 7절대로 딴 기능 브랜치에 쌓고 커밋마다 push 한다 — Phase 4 의 pr-author 는 새 브랜치를 따지 않고 그 브랜치로 PR 을 연다(Phase 4 절 끝의 "여러 커밋으로 나눠 개발한 PR" 문단). 커밋별 산출물 이름은 "싱글턴 지적 교차 검증" 절 (9) C 를 따른다. 모든 커밋이 끝나면 기준 브랜치를 동기화하고 PR 전체를 입력으로 종결 라운드(무지적 3회 + 축 체크리스트)를 돈 뒤 Phase 4 로 간다 — pr-author 의 입력과 pr-reviewer 의 대조 기준은 종결 라운드의 `phase3-review[-rN].md` 다. 9번(런타임 관찰)은 동작이 바뀌는 커밋과 종결 라운드에서 한다("종결 기준·라운드 규약"의 "적용 단위" 절).

개발 중 새 모호점이 나오면 clarifier로 에스컬레이션.

## Phase 4: PR 작성↔점검 루프 (pr-author ⇄ pr-reviewer)

1. `pr-author`가 7절 정책대로 브랜치→PR 생성 (기본 브랜치에서 새 브랜치, 한 PR=한 변경, Conventional Commits).
2. `pr-reviewer`가 base·파일범위·완결성·정합성·롤백성 점검.
3. 변경요청이면 되돌려 수정 → 재점검. 승인까지 루프.

**여러 커밋으로 나눠 개발한 PR:** 1번의 "기본 브랜치에서 새 브랜치"를 하지 않는다 — 커밋이 이미 기능 브랜치에 쌓여 push 돼 있다. pr-author 는 그 브랜치를 그대로 두고(`checkout -b`·재커밋 없음) PR 만 연다. 오케스트레이터는 pr-author 프롬프트에 그 브랜치 이름 · 커밋 목록 · "새 브랜치를 따지 말 것"을 적는다. pr-author 가 "기본 브랜치를 품지 않았다"며 되돌리면 오케스트레이터가 기준 브랜치를 동기화한 뒤 다시 넘긴다(pr-author 정의의 "여러 커밋으로 나눠 개발한 PR" 문단 · "종결 기준·라운드 규약"의 "적용 단위" 절).

## Phase 5: 변경 설명 (change-explainer)

`change-explainer`가 실제 diff 기반으로 사용자용 설명(1절의 언어)을 만든다. **설명을 사용자에게 낸 뒤에만** Stop 훅이 알려 준 `.needs-explain` 경로를 `rm -f` 한다.

**추가 관할 폴더 슬롯 저장소를 고친 세션:** 그 저장소에서 연 PR 의 URL 도
change-explainer 입력에 넣는다. 산문 계약이고 기계 검증은 없다.

## Phase 6: 완료 감사 게이트 (completion-auditor)

사용자에게 "완료"라고 보고하기 **직전**, `completion-auditor`가 모든 완료 주장을 1차 증거로 재검증한다 — 파일 실존·커밋 존재(push≠커밋)·PR 상태·테스트 실제 실행·실제 동작 관찰·**운영 반영 여부(6절)**. 반증이 하나라도 나오면 "완료"라 말하지 않고, 무엇이 실제로 됐고 안 됐는지 정확히 보고한 뒤 해당 주체로 되돌린다.

**이 게이트는 산문이 아니라 훅으로 강제된다** (`.claude/settings.json`). 코드/설정을 편집하면 그 세션 폴더에 `.needs-audit`·`.needs-explain`·`.needs-knowledge`·`.needs-dualreview` 플래그가 서고(설계·계획 산출물은 `.needs-retrieval` 도), Stop 훅이 타입체크(3절, `harness.env`) + **혼자 정하지 않았나** + **머리 표명**(설계·계획 산출물 1줄 회수·2줄 레퍼런스 조사 — 형식을 지키면 스스로 풀린다) + 듀얼 리뷰 + 설명 + **지식 저장소 반영** + push 미완 + 감사 없이는 턴 종료를 막는다(rc=2). 감사자가 검증을 통과시킨 **뒤에만** Stop 훅이 알려 준 `.needs-audit` 경로를 `rm -f` 한다 — 감사 없이 플래그만 지우는 것은 게이트 무력화다. **플래그는 세션마다 따로 있다**(`.claude/.sessions/<세션 번호의 SHA-256 앞 32자>/` — 2026-10-01, 워크트리 세션들이 메인 체크아웃의 플래그 하나를 같이 써서 서로의 종료를 막은 실사고). 세션 번호가 없는 입력만 옛 공유 경로(`.claude/.needs-*`)를 쓴다. **지울 때는 Stop 메시지에 찍힌 그 경로 하나만** 지운다 — 글롭(`.sessions/*/`)이나 다른 세션 폴더를 건드리면 동시에 도는 다른 세션의 게이트를 지운다. 같은 지점에서 진전 없이 3회 차단되면 벽돌 방지 통과되며(게이트를 지울 때마다 카운터 리셋), 그때는 완료 주장을 신뢰하지 말 것.

**추가 관할 폴더 슬롯 저장소를 고친 세션:** 그 저장소의 PR URL 과 그 저장소에
대한 완료 주장도 completion-auditor 입력(완료 주장 목록)에 넣는다. 산문 계약이고
기계 검증은 없다.

**결정 게이트 (2026-08-10 kty 확정 — 이 파이프라인이 겨누는 실패의 부류):** 다른 게이트가 전부 **산출물**을 볼 때 이것만 **네 행동**을 본다. 코드·결정이 바뀐 턴에 결정 표지 어휘를 담은 서술형 문장이 있는데 `AskUserQuestion` 이 0회면 Stop 훅이 막고, 걸린 문장을 목록으로 보여준다.

**지울 플래그가 없다.** 다른 게이트는 일을 마치고 플래그를 지워 푸는데, 이건 **실제로 묻는 것**으로만 풀린다. 보고서에 "이건 이렇게 정했습니다"라고 적는 것은 묻는 것이 아니다 — 정확히 그 행동을 막으려고 만든 게이트다. Phase 1(명료화)이 착수 전에 묻게 한다면 이 게이트는 **작업 중에 새로 생긴 갈림길**을 잡는다. 둘은 같은 가치의 앞뒤다.

걸렸을 때 할 일: ① 걸린 문장이 정말 사용자가 정할 일이었는지 본다 ② 맞으면 `AskUserQuestion` 으로 선택지를 준다 ③ 어휘를 설명·인용한 것뿐이면 백틱이나 따옴표로 감싸면 스캔에서 빠진다(인용은 결정이 아니다). 그래도 걸리면 사용자에게 위양성임을 알리고 지시를 받는다 — **끄지 마라.**

**지식 저장소 반영 게이트 (2026-08-02 kty 확정 — 실사고 재발 방지):** 결정·설계·개발작업이 나온 턴은 종료 전에 지식 저장소에 반영한다.

이 하네스는 **그 저장소가 어디이고 어떤 구조인지 모른다.** 아는 것은 계약 하나뿐이다 — *"지식 저장소가 설정돼 있으면, 결정·설계가 나온 턴은 반영 없이 끝낼 수 없다."* 저장소의 위치·형식·무엇을 어느 파일에 나눠 담는지는 **사용자 층 설정(전역 `CLAUDE.md` 등)이 정본**이다. 그래야 그 저장소를 쓰지 않는 프로젝트에서도 이 하네스가 그대로 돈다(제0원칙 4 — 구체가 아닌 계약에 의존).

절차: ① 사용자 층이 가리키는 규약을 **전문** 읽는다(부분 독해 금지 — `head -N` 사고 전례) ② 그 규약대로 반영하고 **확인 가능한 증거**(커밋 해시·파일 경로)를 확보한다. 결론만이 아니라 그 판단을 만든 **근거(raw)** 도 규약이 정한 자리에 함께 남긴다 — 요약만 남기면 "왜 그렇게 정했나"가 복원 불가능해진다 ③ Stop 훅이 알려 준 `.needs-knowledge` 경로를 `rm -f` 한다.

반영할 지식이 없으면(순수 버그픽스·기계적 수정) 불요 사유를 `_workspace/progress.md`에 기록한다. **completion-auditor 검증 항목에 포함**: 그 증거를 1차 증거로 확인하고, 불요 판정이면 사유의 타당성을 심사한다.

게이트는 **기본 켜짐**이다. 지식 저장소를 쓰지 않는 환경이면 `harness.env`의 `HARNESS_KNOWLEDGE_GATE`를 **비워서** 끈다 (`"off"`라고 적으면 켜진 것으로 읽힌다 — 값이 비어 있지 않기 때문이다).

## Phase 7: 머지 (사용자 승인)

**머지는 사용자 승인 후에만.** 승인 시 프로필 7절의 머지 방식을 따른다(지정 없으면 `gh pr merge --squash --delete-branch`). 머지 후 로컬 기본 브랜치 갱신 + 3절 검증 재확인. 6절에 배포 절차가 있으면 "머지 ≠ 운영 반영"을 사용자에게 명시.

- **진행 기록 = RAM**(`_workspace/progress.md`): **Phase 전환마다 갱신** — 완료 단계 / 다음 단계 / 미해결 결정. 파일 메모리(캐시)에는 진행 로그를 절대 쓰지 않는다 — 캐시는 규칙·확정 결정 전용. Phase 7 완료 시 `_workspace_prev/`로 아카이브(RAM 해제) — 이력은 claude-mem(SSD)·git이 이미 보존한다. claude-mem 비활성/미설치면 `_workspace_prev/`·git 이력이 그 대체 소스다(보고에 "claude-mem 미사용" 명시).

- **프롬프트 주입**(위 주입 규칙): 프로필 섹션·원칙·기억 검색 결과.

## 에러 핸들링

- 에이전트 1회 재시도 후 재실패 시, 결과 없이 진행하되 보고서에 누락 명시. **예외 하나 — 싱글턴 교차 검증(Phase 2·3)은 결과 없이 진행하지 않는다**("싱글턴 지적 교차 검증" 절 (7) 참조).
- 상충 데이터는 삭제하지 말고 출처 병기.
- 파괴적 작업(force push, 브랜치 삭제, 데이터 덮어쓰기)은 실행 전 대상·롤백법 명시하고 필요 시 사용자 확인.
- 프로필이 없거나 해당 절이 비어 있으면: 해당 검증은 "확인 불가"로 명시하고 진행하되, 완료 보고에 "프로필 N절 미작성 — 해당 검증 생략됨"을 남긴다. 지어내지 않는다.

## 진화 신호 감지 (전문 검수자 추가 판단)

"성능/접근성 검수자가 필요한가"를 사람의 기억이나 감에 맡기지 않는다. 신호는 하네스가 쌓고, 판단은 임계치가 한다:

1. **신호 축적**: ecc:code-reviewer dispatch 계약이 지적마다 카테고리 태그(`[성능]` `[접근성]` `[국제화]` 등)를 요구한다. 모든 검수 결과는 claude-mem이 자동 캡처하므로 세션이 끝나도 남는다.
2. **집계·판단**: Phase 6 완료 후, 이번 실행에서 **전문 검수자가 없는 카테고리의 HIGH+ 지적**이 나왔다면 `claude-mem:mem-search`로 같은 카테고리 과거 지적을 검색한다(예: `search(query="reviewer 성능 HIGH")`). **누적 3회 이상**이면 사용자에게 제안한다: "[성능] HIGH 지적이 3회 누적됨 — performance-reviewer를 security-reviewer와 같은 조건부 틀로 추가할까요?"
   **폴백:** claude-mem 비활성/미설치면 자동 캡처·mem-search 대신 검수 누적 카운트를 `.claude/harness/review-counts.md` 파일로 대체한다(검수마다 카테고리·심각도를 한 줄씩 추가·집계) — 보고에 "claude-mem 미사용"을 명시한다.
3. **채택 시 — 만들기 전에 먼저 찾는다**: 자체 제작 전에 `find-skills` 스킬로 스킬 생태계에 기존 해법이 있는지 검색한다(`npx skills find <역량>` — 설치 수 1K+·출처 신뢰도 검증 포함). 쓸만한 것이 있으면 전역 설치(`-g`, 참조 레이어 편입)를 사용자에게 제안하고 끝낸다. 없으면 템플릿 repo(정본)에 에이전트를 추가·커밋하고 각 프로젝트에 sync. 어느 쪽이든 CLAUDE.md 변경 이력에 기록.

> 이 규칙 덕에 "언제 에이전트를 추가하나"가 세션 기억과 무관해진다 — 어느 세션의 오케스트레이터든 같은 검색으로 같은 누적치를 복원한다.

## 결정 기록 (ADR — 결정 시점에 구조화 기록)

**왜 결정 시점인가:** claude-mem(SSD)은 전량 기록이지만 **압축본**이라 추론의 결(기각 사유·트레이드오프)이 손실되고, 사후 추출은 토큰 비용이 크다. 결정이 확정된 **그 자리에서** ADR을 쓴다.

**트리거 (하나라도 해당하면 작성 — 소소한 수정·자명한 선택은 제외, YAGNI):**
- 대안을 기각하고 방향을 확정했다 (아키텍처·라이브러리·패턴·프로세스)
- 대화에서만 확정되고 diff에 드러나지 않는 결정이다
- 사용자가 "이거 기록해 두자 / ADR"이라 말했다

**작성 전 회수 (ADR-0013 ② — 재결정 방지):** ADR 을 쓰기 전에 프로필 9절 진입점에서 선행·관련 결정을 회수한다 — 같은 결정을 다시 내리거나 선행 결정과 모순되는 결정을 쓰는 것을 작성 전에 잡는 자리다. 회수 결과는 ADR 의 "관련" 절에 인용한다(관련 결정이 없으면 `선행 결정 없음` 명시). 첫 줄 표명은 요구하지 않는다 — ADR 첫 줄은 `# ADR-NNNN:` 형식이 이미 계약이다. 이 인용은 pr-reviewer 가 점검한다(산문 검증뿐).

**형식** (`ecc:architecture-decision-records`의 Nygard 형식 — 상세는 스킬 호출로 로드):
파일 `docs/decisions/YYYY-MM-DD-<슬러그>.md`, 제목 `# ADR-NNNN: <결정>`(NNNN=디렉토리 일련번호). 필수 섹션: **Context**(무슨 문제) / **Decision**(무엇으로 확정) / **Alternatives Considered**(대안별 Pros·Cons·Why not) / **Consequences**(Positive·Negative) / **관련**(선행 결정 인용 — 위 회수 규칙).

**작성 주체:**
- 파이프라인 안에서 확정된 결정 → `pr-author`가 **같은 PR에** ADR 포함
- 파이프라인 밖 대화에서 확정된 결정 → 그 자리에서 메인 세션이 작성, docs-only PR로 제출

> progress.md(RAM, 휘발·아카이브)와 다르다: ADR은 **영구 큐레이션** — "왜 이렇게 결정했나"의 원료가 git에 쌓인다(블로그·면접용 사고 과정 포트폴리오).

## 테스트 시나리오

**정상 흐름**: 사용자가 기능 요청(프로필 8절의 예시 유형) → clarifier(범위·대상 확인 질문) → 레퍼런스 조사 판단(필요 시 research-collector→research-evaluator, 불요면 사유 주입) → ecc:planner 계획(머리 표명 2줄) + plan-reviewer 승인 → developer 구현(TDD, `방법론:` 줄) + ecc:code-reviewer 검수 통과 → pr-author PR + pr-reviewer 승인 → change-explainer 설명 → completion-auditor 검증 → 플래그 정리 → 사용자 승인 후 머지.

**에러 흐름**: ecc:code-reviewer가 5절 경계면 shape 불일치 CRITICAL 발견 → developer로 되돌림 → 수정 + 회귀 테스트 → 재검수 통과 → 이후 정상 진행. (또는: Stop 훅이 타입체크 실패로 종료 차단 → developer가 수정 후 재시도.)

## 파이프라인 밖: 상시 자문 에이전트

`architecture-guide`는 개발 흐름에 속하지 않는다. 사용자가 "이거 왜 이렇게 짰냐 / 남이 물으면 뭐라 답하지"처럼 **구조의 설계 의도**를 물을 때 직접 호출한다(프로젝트 아키텍처·하네스 둘 다). `change-explainer`(특정 PR의 변화)와 구분: 이쪽은 서 있는 구조의 근거. 코드 변경이 없으므로 이 파이프라인을 타지 않는다.

## 후속 작업

"다시/재실행/보완/수정/이전 결과 기반" 요청은 Phase 0에서 `_workspace/` 확인 후 해당 에이전트만 부분 재실행한다(리뷰 게이트면 그 Phase 의 cc·cx 한 쌍). 각 에이전트는 이전 산출물이 있으면 읽고 델타만 반영한다. "검수만 다시" → Phase 3 검수만(2–7번 그대로 — ecc:code-reviewer 와 codex 는 같은 메시지로 동시 발사), "PR만 다시" → Phase 4만(pr-author 가 PR 을 갱신하고, 점검은 pr-reviewer 와 codex 동시) — 단 그 결과가 앞 단계 산출물과 모순되면 해당 앞 단계로 되돌린다.
